1. Executive Summary

mendix-test-agent is a browser-testing platform built around one idea: the expensive, error-prone part of end-to-end testing isn't clicking through a flow once — it's turning that flow into a test that stays correct as the application under test keeps changing. This project automates exactly that transition, and then keeps the resulting test alive automatically instead of letting it quietly rot.

A tester records a flow the same way they'd manually test it — logging in, clicking through a scenario, no code. An LLM (Groq, OpenAI-compatible) then rewrites that raw recording into a real Playwright test: stable locators, explicit assertions inferred from what actually happened, proper asynchronous waits instead of fixed sleeps, and BDD-style step labels. Every AI-generated change — a brand-new test, a re-recording, or a proposed fix to a broken locator — goes through a mandatory human review queue before it ever reaches the real test suite. Nothing the AI writes is trusted blindly.

Beyond generation, the platform actively maintains its own tests: it detects when a locator breaks and proposes a grounded fix (never an invented one — always checked against a live replay of the real application), diagnoses failures in plain English, scores every test's maintainability, flags flaky tests from real run history, and — a genuinely novel piece — can reach directly into the application's own database to clear stuck sessions and diagnose authorization gaps between user roles.

In one sentence: it turns "someone tested this once by hand" into "this is permanently, automatically re-tested, and the tests fix themselves when the application's UI changes underneath them."

2. Problem & Value Proposition

The problem this solves

  • Manual regression testing doesn't scale. Every UI change risks breaking something a human tested once and never re-checks.
  • Hand-written E2E tests are expensive and brittle. Writing a Playwright test by hand for every flow is slow; the locators it depends on break the moment a widget gets renamed, and someone has to notice, diagnose, and fix it.
  • Low-code platforms change fast and can't be inspected programmatically. There's no access to a Mendix Studio Pro project's internal model from outside it — the only ground truth available to an external tool is what a real browser session actually renders.
  • Trial/dev licenses impose real operational constraints (session/seat limits) that most testing tools ignore entirely, and that silently produce false failures if not actively managed.

4. System Architecture

The system has four cooperating layers: a thin web UI, a library of CLI scripts that do the actual work (and that the UI simply orchestrates), the generated Playwright test suite itself, and the application under test — reached two ways: through the browser, like a real user, and, for maintenance operations, directly against its database.

Key architectural decisions

  • The UI is a thin wrapper, never the source of truth. Every button runs the same CLI command a person could type directly — nothing about the underlying scripts changes based on whether they're invoked from a browser or a terminal, which is also why CI uses the CLI path exclusively.
  • Nothing AI-generated is trusted automatically. A brand-new test, a re-recording, or a locator fix all land in a pending-review queue as a before/after diff. A hardcoded-secret check runs before a proposal can even be approved.
  • Every locator decision is grounded in a live replay, never a guess. Whether generating a new test or fixing a broken one, the model only ever sees — and is only allowed to choose from — widgets that a real, just-now browser session actually rendered.
  • Multi-project, multi-role, multi-environment by design. The same installation can test several separate applications, each with its own roles and credentials, each runnable against several named environments (Default, QA, Staging...) with zero test-source changes.

5. Core Workflow — Record → Enrich → Review → Run

This is the primary path from "someone tested a flow by hand" to "this is a permanent, self-maintaining automated test."

flowchart TD Start([Tester wants to cover a new flow]) --> Record[Record: Playwright codegen\nopens a real browser\ntester logs in and clicks through manually] Record --> Raw[Raw, unpolished recording\ndumb clicks/fills, no assertions] Raw --> Snapshot[Replay the recording once more,\nstep by step, capturing every real\nmx-name-* widget visible at each step] Snapshot --> Enrich{Send recording + live\nwidget snapshot to the AI} Enrich --> Draft[AI drafts a maintainable test:\nstable locators, real assertions,\nMendix-aware waits, BDD step labels] Draft --> SecretCheck{Hardcoded secret\ncheck} SecretCheck -->|fails| Reject[Refused - never written,\nstays in the recording only] SecretCheck -->|clean| Pending[Pending review queue:\nbefore/after diff + quality score] Pending --> Human{Human reviews} Human -->|Reject| Discard[Discarded - raw recording\nkept for a retry] Human -->|Regenerate| Enrich Human -->|Approve| Live[Written to generated-tests/\n+ derived .feature doc] Live --> CI[Runs on every push/PR/nightly\nvia GitHub Actions] CI --> Report[HTML report + JUnit +\nAI failure diagnosis on any failure] Report --> Monitor[Tests tab: quality score,\nflaky detection, pass/fail history]

Self-healing sub-workflow: Update / Analyze / Extend

Once a test exists, it doesn't just sit there waiting to break. Three grounded maintenance paths cover everything that can go wrong with an existing test, all converging on the same review queue:

flowchart LR subgraph Trigger["Something needs fixing"] A["A locator stopped\nresolving (widget renamed)"] B["The whole scenario\nchanged"] C["The scenario grew\nnew steps at the end"] end A --> Analyze["Analyze and heal locators\nRun the test's own steps live,\ncollect every real widget seen,\npropose a fix only above a\nconfidence threshold"] B --> Update["Update (re-record)\nRecord the whole flow again;\ndiff against current code,\nnot the old raw recording"] C --> Extend["Extend (record more)\nReplay existing steps to a\nlogged-in point, record only\nthe NEW tail, splice it in\ndeterministically - no AI\nrewrite of the whole file"] Analyze --> Queue[(Pending review queue)] Update --> Queue Extend --> Queue Queue --> Approve{Human approves?} Approve -->|yes| Patch[Existing test patched/replaced] Approve -->|no| Nothing[Nothing changes]
The Extend path is a deliberate design choice worth calling out: instead of asking the AI to reproduce an entire file (risking a subtle corruption of code that was already passing), only the new tail is AI-generated, and it's spliced into the existing file by plain, deterministic text manipulation — the model never touches the parts of the file that already worked.

6. How the AI Generation Actually Works

The same "replay first, ask the model to choose only from what's real" pattern is reused, unmodified in spirit, for every AI-touched feature in the project: new-test generation, locator healing, and the natural-language-to-test-plan generator. None of them ever let the model invent a selector from nothing.

8. How To Use It (Brief)

  1. Setup: npm install, npx playwright install --with-deps chromium, fill in a Groq API key and the app's URL/credentials in .env.
  2. Open the UI: npm run ui → http://localhost:4300, pick or create a project.
  3. Record a flow: Review tab → Record → log in as a role and click through the scenario like a real manual test → close the recorder window.
  4. Review the AI's draft: a before/after diff with a quality score appears in Pending Review → Approve, Reject, or Regenerate.
  5. Run it: Runs tab (one role, one file, by tag, or everything) — or let CI run it on every push automatically.
  6. When something breaks: Fix an existing test → Analyze & heal locators (renamed widget), Update (scenario changed), or Extend (scenario grew) — review and approve the proposed fix like anything else.
  7. Keep an eye on health: Tests tab for quality/flaky trends, Insights tab for performance/regression/coverage/authorization.
The CLI equivalent of every UI action is documented in TESTING_GUIDE.md — the UI is optional, never the only way to do something.

9. Is This Mendix-Only?

Honest answer: the architecture is general-purpose; the current implementation is Mendix-coupled in a specific, identifiable layer. The two need to be judged separately.

What's already generic (reusable for any Playwright-drivable app)

  • The whole record → AI-enrich → human-review → run pipeline and its orchestration.
  • Multi-project / multi-role / multi-environment project structure.
  • The pending-review queue, quality scoring, flaky detection, AI failure diagnosis.
  • The Update / Analyze / Extend self-healing pattern — the mechanism ("replay live, only propose from what's real, splice deterministically") is not Mendix-specific at all.
  • CI wiring, secret-leak validation, reporting, the whole UI shell.

What's currently Mendix-specific

ComponentWhy it's Mendix-coupled today
Locator strategy (BasePage.mx()) Relies on Mendix's own mx-name-<WidgetName> CSS class convention — effectively Mendix's built-in data-testid equivalent
AI system prompts (enrich.js, heal-scan.js) Written with explicit Mendix knowledge: the mx-name-* convention, waitForMendixIdle(), the /xas/ API pattern
Session/seat-cap handling Specific to how a Mendix trial license enforces concurrent-session limits
Database-level tooling (session reset, entity-mapping utilities) Hardcoded against Mendix's own internal schema conventions (system$session, system$user, mendixsystem$*)

What it would take to target a different stack

For a React/Vue/Angular/plain-HTML application with a stable locator convention (data-testid, aria-label, or similar), porting this platform would mean:

  1. Swap BasePage's locator helper for whatever stable attribute the target framework guarantees.
  2. Rewrite the AI system prompts to reference that convention instead of mx-name-*, and remove Mendix-specific async-wait guidance.
  3. Drop (or reimplement against the target's own persistence layer) the database-level session/authorization tooling — those are inherently platform-specific by nature, not just by current implementation.
Bottom line: a team adopting this for a non-Mendix application keeps roughly the entire orchestration, review, AI-diagnosis, and CI layer as-is, and needs to rebuild only the locator-and-prompt adapter layer plus any platform-specific database utilities. It is not a Mendix-only tool in principle — it is a Mendix-first implementation of a general pattern.

10. Known Limitations & Constraints

  • Trial license seat cap (local/dev Mendix instances): concurrent-session limits can cause false failures under load; mitigated with serial execution, retries, and automatic session clearing, but not eliminated on a genuinely tiny trial cap.
  • No access to the Studio Pro project model. Every feature is grounded in what a real browser session (or, for DB tooling, the app's own database) can observe — by design, but it means nothing here can reason about microflows/entities it hasn't actually seen exercised.
  • Self-healing requires a confident match. A locator with no plausible replacement among currently-visible widgets is reported as unresolved, never guessed — correct behavior, but it means some fixes still need a human.
  • Extend mode is single-scenario only. A spec with multiple test() calls in one describe block isn't a supported target yet.
  • Data cleanup is opt-in and manual where no verified delete flow has been recorded — the project deliberately refuses to fabricate a delete step from a guessed locator.

11. Conclusion

mendix-test-agent demonstrates that the most expensive part of end-to-end testing — keeping tests alive as the application changes — can be substantially automated without sacrificing trust, as long as every automated decision stays grounded in something real and every AI-authored change passes through a human before it counts. The result is a testing practice that costs a single manual pass per flow instead of a manual pass every time someone wants to be sure a flow still works.
